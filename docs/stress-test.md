# 壓力測試（階段 4-1）

```bash
npm run stress
```

```bash
npm run stress -- --out dist
```

第二行會另外把模擬資料存成 `dist/stress-*.json`，可以在測試用的部署中，用「擁有者 → 系統與備份 → 匯入資料」匯入，實際量測 Google 上的速度。名字都是假資料。

## 模擬情境

一年 48 堂，出席率 85%，每位出席學員平均加扣分 1.5 次，每堂一次小隊加分，每 8 週開放兌換。試算表讀寫是記憶體模擬，**不含 Google 的網路與試算表延遲**，所以數字是程式本身的下限。

## 結果（2026-10-24，Node 22）

| | 小型 1 班 × 30 人 | 中型 3 班 × 50 人 | 大型 5 班 × 80 人 |
|---|---|---|---|
| 流水帳筆數 | 2,931 | 14,688 | 39,315 |
| 資料大小 | 0.87 MB | 4.34 MB | 11.59 MB |
| 試算表儲存格數 | 23 | 114 | 304 |
| 單機版 localStorage 用量（約 5M 字元） | 17% | **87%** | **232%** |
| 一次點名：後端耗時 | 23 ms | 220 ms | 628 ms |
| 一次點名：回傳給瀏覽器 | 0.87 MB | **4.34 MB** | **11.60 MB** |
| 每 30 秒輪詢：傳輸大小（壇務） | 0.87 MB | 4.35 MB | 11.60 MB |
| 每 30 秒輪詢：傳輸大小（訪客） | 0.59 MB | 2.93 MB | 7.82 MB |

一次點名的後端耗時，主要分成四段：讀取並解析資料、套用操作（會先複製整份資料）、寫回試算表、把整份資料序列化後回傳。這四段都跟資料大小成正比。

## 發現的問題

1. **每次操作都回傳整份資料**：中型規模每按一次點名，就要傳 4 MB 回手機，訪客輪詢也是整份傳送。手機網路下會明顯變慢，也會消耗流量。這是最大的瓶頸。
2. **單機版容量不足**：中型規模一年用掉約 87% 的 localStorage，跨年度結算時還要再存一份備份，會因為空間不足而失敗；大型規模在年中就存不下了。
3. **後端耗時跟資料量成正比**：每次操作都要讀寫、複製整份資料。實際在 Google Apps Script 上還要加上試算表讀寫與網路時間，只會更慢，而且操作期間會鎖住，其他人要排隊（鎖定最多等 15 秒）。

## 建議改善方向

- **寫入後只回傳變動**（回傳 `rev` 與新增或修改的項目），輪詢時如果 `rev` 沒變就不傳資料。這樣不用改資料結構，效果也最大。
- 流水帳瘦身：省略空欄位、`operatorName` 改由 `operatorId` 對應，實測約可減少 22% 的大小，效果有限。
- 單機版定位為小型班別使用，在用量超過 70% 時提醒擁有者下載備份。
- 部署到測試試算表後，匯入 `stress-medium.json` 實測真實延遲，確認改善的優先順序。
